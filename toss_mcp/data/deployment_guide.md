# 앱인토스 배포 실전 가이드

이 가이드는 앱인토스 공식 문서의 빌드·업로드·검토 절차를 보완하는 범용 체크리스트다. 프로젝트 이름, 환경변수 이름, API 주소, React Native 버전은 각 프로젝트 설정에 맞게 바꿔 사용한다.

## 1. 배포용 앱 번들 만들기

프로젝트가 제공하는 build 스크립트로 `.ait` 파일을 만든다.

```bash
pnpm build
```

빌드 전에 `granite.config.ts`의 `appName`이 앱인토스 콘솔에 등록한 앱 이름과 같은지 확인한다. API 주소나 기능 플래그처럼 번들러가 빌드 시점에 치환하는 값은 셸 또는 프로젝트의 배포용 환경 파일에 먼저 주입해야 한다.

## 2. 업로드 전 산출물 검증

빌드 로그와 타입 검사가 성공해도 특정 플랫폼 또는 호환 React Native 번들에 환경값이 빠질 수 있다. 업로드 전에 `.ait` 안의 모든 iOS·Android JavaScript 번들을 열어, 공개 API 호스트 같은 안전한 식별자가 실제로 포함됐는지 확인한다. 비밀키나 토큰을 검사값으로 사용하거나 클라이언트 번들에 넣으면 안 된다.

아래 예시는 SDK 버전을 하드코딩하지 않고 현재 산출물의 번들 목록을 찾는다.

```bash
AIT_FILE="${AIT_FILE:?검증할 .ait 파일 경로를 지정하세요}"
EXPECTED_API_HOST="${EXPECTED_API_HOST:?번들에 포함돼야 할 공개 API 호스트를 지정하세요}"

bundle_files=$(unzip -Z1 "$AIT_FILE" 2>/dev/null | grep -E '^bundle\.(ios|android)\..+\.js$' || true)
if [ -z "$bundle_files" ]; then
  echo "검증할 iOS/Android JavaScript 번들을 찾지 못했습니다." >&2
  exit 1
fi

failed=0
while IFS= read -r bundle_file; do
  match_count=$(unzip -p "$AIT_FILE" "$bundle_file" 2>/dev/null | grep -F -c "$EXPECTED_API_HOST" || true)
  printf '%-40s %s\n' "$bundle_file" "$match_count"
  if [ "$match_count" -eq 0 ]; then
    failed=1
  fi
done <<EOF
$bundle_files
EOF

if [ "$failed" -ne 0 ]; then
  echo "일부 번들에 기대한 환경값이 없습니다. 환경 주입을 고친 뒤 다시 빌드하세요." >&2
  exit 1
fi
```

필요하면 다음 항목도 함께 확인한다.

- 생성된 iOS·Android 및 호환 버전 번들의 개수가 현재 SDK가 기대하는 개수와 같은가
- 프로덕션 API가 HTTPS를 사용하고, 실제·QR 테스트 Origin이 서버 CORS 허용 목록에 있는가
- mock API, 디버그 UI, 내부 오류 표시 같은 개발 전용 플래그가 꺼져 있는가
- 앱 아이콘과 `appsInToss` brand 필수값이 비어 있지 않은가
- 압축 해제한 번들 크기가 공식 제한을 넘지 않는가

`.ait`는 ZIP 데이터 앞에 메타데이터가 포함될 수 있어 `unzip`이 앞부분의 추가 바이트를 경고할 수 있다. 파일 목록과 번들 내용을 정상적으로 읽을 수 있다면 이 경고 자체는 손상 판정 근거가 아니다.

## 3. CLI로 번들 업로드

콘솔의 키 메뉴에서 API 키를 발급한다. 로컬 개발 환경에서는 최초 한 번 토큰을 등록하면 이후 명령에서 키를 반복 입력하지 않아도 된다. 자격 증명 파일은 버전 관리에 포함하지 않는다.

```bash
pnpm exec ait token add
pnpm exec ait deploy -m "변경 내용을 식별할 수 있는 출시 메모"
```

프로젝트가 pnpm을 사용하지 않으면 같은 CLI를 `npx ait ...` 등 해당 패키지 매니저 방식으로 실행한다. CI에서는 저장 토큰 대신 비밀 저장소에서 API 키를 주입하고, 로그나 산출물에 키가 남지 않게 한다.

CLI 업로드가 실패하면 다음을 우선 확인한다.

- `granite.config.ts`의 `appName`과 콘솔 앱 이름이 일치하는가
- 올바른 워크스페이스·앱 권한이 있는 API 키인가
- SDK가 CLI 업로드를 지원하는 버전인가
- 서버 측 번들 처리 실패 사유가 콘솔에 표시되는가

CLI 업로드는 앱 번들을 등록하고 처리 결과를 기다리는 단계다. 검토 요청이나 실제 출시는 대신하지 않는다.

## 4. 콘솔 테스트·검토·출시

1. 업로드된 번들로 QR 테스트를 최소 한 번 완료한다. 테스트 사용자는 토스 로그인, 해당 워크스페이스 멤버, 연령 등 공식 테스트 조건을 충족해야 한다.
2. 게임·비게임 출시 가이드와 체크리스트를 확인한 뒤 콘솔에서 검토를 요청한다. 검토는 한 번에 한 버전만 요청할 수 있다.
3. 승인된 번들을 콘솔에서 출시한다. 출시하면 전체 사용자에게 즉시 반영되므로 마지막으로 대상 버전과 출시 메모를 확인한다.

검토 중 오류를 발견하면 요청을 취소하고 수정한 새 `.ait`를 업로드한 뒤 다시 검토를 요청한다. 검토 기간은 보통 영업일 기준 최대 3일이지만 앱 카테고리에 따라 7일 이상 걸릴 수 있으므로 최신 공식 문서를 기준으로 일정을 잡는다.

## 5. 출시 직후 확인

QR 테스트와 실제 환경은 Origin, 네트워크, 권한, 로그인·세션, 결제·인증 동작이 다를 수 있다. 출시 직후에는 다음을 확인한다.

- 주요 사용자 흐름과 딥링크가 실제 앱에서 열리는가
- API 오류율, 응답 지연, 크래시·오류 로그에 이상이 없는가
- 외부 이미지·폰트·CDN 리소스가 안정적으로 로드되는가
- 결제, 인증, 권한 요청처럼 실제 환경 의존 기능이 정상인가

문제가 생기면 콘솔에서 이전 승인 버전으로 롤백할 수 있는지 확인하고, 심각한 실행 오류는 앱인토스 공식 지원 채널에 문의한다.
